# Data handling

The site uses public branding and synthetic workflow screenshots and videos. The example clinical note is fictional and requires physician review. No real patient record, credential, cookie, or crawler cache belongs in this site subsystem.

The contact form accepts general questions only. Its endpoint validates input and stays unavailable without `RESEND_API_KEY` and `RESEND_FROM_EMAIL`; messages go to `CONTACT_RECIPIENT`, or `info@sentrapedia.com` when it is unset. The endpoint only accepts a browser `Origin` that matches the site itself. `CONTACT_PUBLIC_ORIGIN` pins that origin to one exact value (scheme and host, for example `https://sentrapedia.example`; a trailing slash is ignored, and a malformed value rejects every browser submission). It is optional; setting it in Vercel's Production environment once the public domain is final makes the accepted origin explicit. When it is unset, the endpoint expects the request's own host with the scheme Vercel reports in `x-forwarded-proto` (HTTPS on Vercel, including previews; HTTP on the local server). These names document configuration; values are never stored in the repository.

Rate limiting: the endpoint keeps a per-IP count (5 per 15 minutes), but it lives in one function instance's memory, so on Vercel it only slows bursts that land on the same warm instance. The durable limit is a Vercel Firewall rate-limit rule on `POST /api/contact` keyed by IP, rolled out in `log` mode first; it is a hosting setting, applied by Gaffer, not by this repository. A production sender and live delivery require a separate review and authorization. Local tests use synthetic inputs and mock acceptance only.

Migration copies only files listed in `migration-manifest.json`; optional authoring captures and historical browser evidence remain in the independent source checkout. Keep any future source media synthetic and record provenance before copying it here.
